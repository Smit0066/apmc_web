01 · EXECUTIVE OVERVIEW

આ સિસ્ટમ શા માટે ઉપયોગી બની શકે?

માર્કેટ યાર્ડમાં વાહન આવક, માલની ઓળખ, હરાજી ભાવ, વજન, ખેડૂતને ચુકવણી, વેપારી પાસેથી વસૂલાત અને Gate Pass અલગ-અલગ કાગળમાં હોય તો yard stock તથા બાકી રકમની સાચી સ્થિતિ તરત સમજવી મુશ્કેલ બની શકે. YardOSનો પ્રસ્તાવ આ બધું એક Lot ID, party identity અને transaction trailથી જોડે છે.

01 · ખેડૂતને પુરાવો

ભાવ-કાપલી હવે શોધી શકાય તેવો record

દરેક auction recordને serial number આપવો. ખેડૂત અને ખરીદદારને તેમની નકલ આપવી અને યાર્ડ પાસે central record રાખવો.

02 · યાર્ડ ઓફિસને નિયંત્રણ

Live-style Yard Control

કેટલા વાહન આવ્યા, હરાજી કેટલી થઈ/બાકી છે, કેટલો માલ yardમાં કોનો છે, કેટલો રવાના થયો અને કઈ deadline વટાવી - એક જ dashboardમાં.

03 · વિવાદમાં traceability

Lotથી bill સુધી સીધી કડી

ફરિયાદ વખતે ખેડૂત, પાક, buyer, ભાવ, વજન અને ચુકવણીની જોડાયેલી વિગતો શોધવાનો રસ્તો મળે.

04 · મેનેજમેન્ટ માટે MIS

રિપોર્ટ અને જવાબદારી

Farmer payable/paid/balance, trader purchase collection/outstanding, credit limit, overdue stock અને activityના records.

એક વ્યવહારનો સંપૂર્ણ પ્રવાહ

01 · GATEઆવક નોંધખેડૂત + વાહન + પાક → Lot ID
02 · AUCTIONભાવ-કાપલીBuyer + ભાવ + જથ્થો → serial ticket
03 · WEIGHવજનGross - Tare = Net
04 · BILLવેચાણ બિલNet weight × auction rate
05 · ACCOUNTSચુકવણીચૂકવેલ + બાકી + reference
06 · BUYER DUESખરીદદાર હિસાબbuyer-side dues અલગ track
07 · GATE PASSમાલ રવાનાચકાસણી પછી pass
08 · CREDITવેપારી ખાતુંRegistration + credit days + limit
09 · AUDITરેકોર્ડ / રિપોર્ટSearch + export + activity trail
સૌથી મહત્વની બાબત: દરેક Lot ID સાથે માલિક/વેચનારની ઓળખ, હરાજી ticket, વજન, farmer payment deadline, stock-removal deadline અને buyer credit balance જોડાય છે. Dashboardથી મેનેજમેન્ટને “હાલ yardમાં શું પડ્યું છે અને કોનાં પૈસા બાકી છે?” તેનો જવાબ એક જ જગ્યાએ મળે.

02 · USER ROLES & DAILY OPERATION

દરેક કર્મચારી પોતાનું કામ જ કરે

Role-based accessથી દરેક વિભાગને જરૂરી screen સુધી પહોંચ મળે અને અન્ય વિભાગોની sensitive settings અનાવશ્યક રીતે ખુલ્લી ન રહે.

Administrator / પ્રશાસકસંપૂર્ણ overview, master settings, role control અને તમામ રેકોર્ડનું નિરીક્ષણ.
Gate Operator / ગેટ કર્મચારીખેડૂત-વાહન આવક નોંધ, Lot ID, gate pass અને vehicle exit.
Auction Operator / હરાજી કર્મચારીLot પસંદ કરવો, buyer અને ભાવ નોંધવો, ticket issue અને print.
Weighment Operator / તોલ કર્મચારીGross, tare, scale reference અને net weight નોંધવો.
Accounts / એકાઉન્ટ્સSale bill, farmer settlement, buyer-side dues અને payment reference.
Inspector / નિરીક્ષકફરિયાદની તપાસ, resolution note અને audit records review.

03 · SCREEN-BY-SCREEN GUIDE
01

Dashboard / આજની યાર્ડ સ્થિતિ

વાહન આવક, હરાજી, yard stock, ખેડૂત ચુકવણી, વેપારી બાકી અને deadlineનું central control screen.

Screenshot 01 · Original dashboard widgets retained + new Yard Control panels added
આ SCREEN શા માટે?

જૂના dashboardના ચાર summary cards (કુલ આવક, હરાજી પૂર્ણ, ખેડૂત ચુકવણી બાકી અને ખુલ્લી ફરિયાદ), દૈનિક હરાજી કામગીરીનો graph, તાજેતરની પ્રવૃત્તિ, quick actions અને recent lots જાળવવામાં આવ્યા છે. તેની નીચે નવા indicatorsથી કેટલા વાહન/લોટ આવ્યા, હરાજી બાકી, Gate Pass જારી, માલ રવાના અને હાલમાં કોનો કેટલો માલ yardમાં છે તે દેખાય છે.

અહીં શું દેખાય છે?

કુલ વાહન/લોટ આવક, હરાજી પૂર્ણ/બાકી, Gate Pass અને dispatched lots, yardમાં રહેલા lots અને કુલ ક્વિન્ટલ; ખેડૂત payable/paid/balance તથા વેપારી પાસેથી મળેલી/બાકી ખરીદ રકમ. નીચે lot-wise stock tableમાં માલિક, પાક, વાહન, ખરીદદાર, stage અને dispatch deadline દેખાય છે.

USERએ શું કરવાનું?

મોટાભાગે dashboard જોવો અને જે યાદી પર કામ કરવું હોય તેમાંથી Lot detail ખોલવો. નવી આવક માટે “નવી ગેટ એન્ટ્રી”, હરાજી માટે Auction, તોલ માટે Weighment અને વેપારી વસૂલાત માટે Trader Account ખોલવું.

શું AUTOMATIC થશે?

જૂના activity graph અને recent activity feed dashboard પર જ રહે છે. નવી entry, auction ticket, weighment, farmer payment અને gate exit પછી સંબંધિત counters, stock quantity, outstanding balances અને overdue alerts પણ update થાય છે. Demoમાં આ browser sample data પરથી છે; productionમાં central databaseમાંથી real-time update કરવાના.

ફાયદો: Yard managerને “કેટલો માલ આવ્યો? કેટલો વેચાયો? કેટલો હજી અંદર છે? કોને ચુકવવાનું છે? વેપારી પાસેથી કેટલું લેવાનું છે? કઈ deadline વટાવી?” એ પ્રશ્નોના જવાબ એક જ screen પરથી મળે.

04 · SCREEN-BY-SCREEN GUIDE
02

Gate Entry / ગેટ એન્ટ્રી અને આવક

ખેડૂત અને માલ યાર્ડમાં પ્રવેશે ત્યારે પ્રથમ નોંધ.

Screenshot 02 · Gate Entry register
આ SCREEN શા માટે?

યાર્ડમાં આવતાં દરેક વાહન અને માલની એક સરખી અને શોધી શકાય તેવી entry બનાવવા માટે.

અહીં શું ભરવાનું?

વેચનાર ખેડૂત છે કે વેપારી તે પસંદ કરવું. ખેડૂત માટે Farmer Registry/AgriStack ID અને લાગુ રાજ્યનો 7/12, 8A અથવા RoR reference; વેપારી માટે APMC Registration/Licence ID. સાથે નામ, મોબાઇલ, રાજ્ય/જિલ્લો/તાલુકો/ગામ, પાક, બેગ, વાહન, અંદાજિત વજન અને grade.

USERએ શું કરવાનું?

“નવી ગેટ એન્ટ્રી” ક્લિક કરીને વિગતો ચકાસવી અને Save કરવું. ત્યારબાદ lot registerમાં entry દેખાશે.

શું AUTOMATIC થશે?

Unique Lot ID અને arrival timestamp બનશે; party type, seller ID અને land/licence reference Lot સાથે link થશે. એ જ IDથી auction, weighment, bill, payment અને dispatch સુધી record જોડાશે.

ફાયદો: વાહન, ખેડૂત કે પાકની શોધ Lot ID અથવા વિગતો પરથી કરી શકાય. એક જ માલ માટે જુદા-જુદા કાગળમાં ફરીથી ઓળખ લખવાની જરૂર ઘટે.

05A · SELLER IDENTITY & NATIONAL FARMER RECORDS
02A

ખેડૂત / વેપારી ઓળખ અને Land Record

એક જ Lot સાથે યોગ્ય party type અને અધિકૃત ઓળખનો reference જોડવો.

Screenshot 02A · Gate entry form with farmer / trader identity fields
ખેડૂત હોય તો શું ભરવું?

Farmer Registry / AgriStack Farmer ID ઉપલબ્ધ હોય તો તે, રાજ્યનું નામ, જિલ્લો, તાલુકો, ગામ અને લાગુ land-record reference. ગુજરાતમાં 7/12 અથવા 8A; અન્ય રાજ્યોમાં Khasra/Khatauni, RTC/Pahani, Patta અથવા State RoR/Survey reference.

વેપારી / રજીસ્ટર્ડ seller હોય તો?

Party type “વેપારી” પસંદ કરીને APMC-issued Trader Registration / Licence ID દાખલ કરવો. Ticket પર seller type “વેપારી” અને registration reference દર્શાવાશે.

SYSTEMમાં શું થશે?

આ identity fields Lot ID સાથે link થશે. Auction ticket પર વેચનાર ખેડૂત છે કે વેપારી તે અલગ દેખાશે; Farmer Registry / land record અથવા Trader Registration ID ticket પર print થશે.

APMCએ શું verify કરવું?

રાજ્યની અધિકૃત Farmer Registry / RoR service, tenant/sharecropperની માન્યતા, farmer consent, data access અને trader licence validation. માત્ર data entryથી સરકારી recordનું automatic verification થયું એમ માનવું નહીં.

ખાસ સમજણ: 7/12 આખા ભારતનો એકસરખો document નથી. ગુજરાતમાં 7/12 ઉપયોગી છે; બીજા રાજ્યોમાં પોતાનો land-record format હોય છે. AgriStack Farmer ID રાજ્યના digitised land records સાથે જોડાય છે અને State/UT registry દ્વારા જાળવાય છે. Official Farmer Registry FAQ ↗
Aadhaar numberને APMC ticketમાં છાપવાની કે અહીં સીધી રીતે સંગ્રહવાની જરૂર નથી. Actual Farmer Registry verification માટે government-authorized API, farmer consent અને role-based access જરૂરી છે.

03

Auction & Digital Price Slip / હરાજી અને ભાવ-કાપલી

આ સમગ્ર conceptનું મુખ્ય proof-of-transaction module.

Screenshot 03 · Auction register / price discovery
આ SCREEN શા માટે?

હરાજીમાં નક્કી થયેલો ભાવ કાગળની નાની કાપલી સુધી મર્યાદિત ન રહે; unique serialવાળા digital recordમાં સંગ્રહિત થાય.

USERએ શું ભરવાનું?

હરાજી માટે તૈયાર Lot પસંદ કરવો, buyer, quality, quantity, final rate per quintal, auction method અને નોંધ દાખલ કરવી. Lot સાથે જોડાયેલ seller type અને farmer/trader identity પણ ચકાસવી.

શું AUTOMATIC થશે?

Ticket serial number બનશે; Lot ID, seller identity, buyer registration અને price link થશે. Settingsમાંથી ખેડૂત payment due days, stock-removal days અને buyer credit days વાંચીને due dates auto-generate થશે.

કઈ નકલો / પુરાવો?

Designમાં ખેડૂત, ખરીદદાર અને યાર્ડ office માટે 3 print copiesનો વિચાર છે. QR-based lookup અને cancellation/correction policy productionમાં મજબૂત રીતે અમલમાં મૂકવાની ભલામણ છે.

મુખ્ય ફાયદો: વિવાદ થાય ત્યારે “કાપલી કોની પાસે છે?” એ પર આધાર રાખવાને બદલે ticket number/Lot ID પરથી હરાજીનો record શોધી શકાય. આ જ આ પ્રસ્તાવનો સૌથી વધુ મૂલ્યવાન ભાગ છે.
Productionમાં ticket issue પછી સીધું overwrite ન થવું જોઈએ. ભૂલ સુધારવા reason, approval, old value/new value અને original ticket history સાથે correction/cancellation entry બનાવવી.

Digital Price Slip / ભાવ-કાપલીનું preview

હરાજી પૂરી થયા પછી operatorને મળતું print-ready ticket concept.

Screenshot 03A · Demo ticket preview; sample transaction only
TICKET IDENTIFICATION

Unique serial number

દરેક ticketને APMC-26 પ્રકારનો અલગ serial number આપવાનો પ્રસ્તાવ છે. આ નંબર બોલીને અથવા searchમાં નાખીને transaction શોધી શકાય.

TRANSACTION DETAILS

એક જ slipમાં જરૂરી માહિતી

Seller type (ખેડૂત/વેપારી), Farmer Registry ID સાથે લાગુ state land record અથવા Trader Registration ID, Lot ID, પાક/grade, buyer અને buyer licence ID, વેચાયેલ જથ્થો, પ્રતિ ક્વિન્ટલ ભાવ, તારીખ/સમય અને ત્રણ due dates.

THREE-COPY CONTROL

ત્રણ હિતધારકો માટે નકલ

Seller copy, Buyer copy અને Yard copy. એકસરખો serial, party identity, buyer registration, farmer payment deadline, dispatch deadline અને trader credit due date દરેક copy પર.

QR & VERIFICATION

સ્કેનથી record શોધવાની સુવિધા

QRમાં ticket reference રાખીને approved userને verified record સુધી લઈ જવાનો વિકલ્પ. Public QR access અને data privacy production designમાં નક્કી કરવું.

Slip પર દેખાતી due dates Settingsમાં દાખલ કરેલા sample defaults પરથી auto-generate થાય છે; તે કાયદામાં નક્કી કરેલી universal મર્યાદા નથી. Productionમાં APMC resolution, current Rules/bye-laws અને લાગુ licence conditionsથી મંજૂર દિવસો જ configure કરવા. Real QR verification, signed lookup, official serial allocation અને duplicate-print tracking હજી production requirements છે.

Weighment / વજન કાંટા વ્યવસ્થાપન

હરાજી ticketને actual gross, tare અને net weight સાથે જોડવું.

Screenshot 04 · Weighment queue and records
આ SCREEN શા માટે?

હરાજીમાં થયેલા વ્યવહાર સામે વાસ્તવિક તોલનો record રાખવો અને estimated quantityના બદલે net weight પરથી bill તૈયાર કરવું.

USERએ શું ભરવાનું?

સંબંધિત Lot પસંદ કરવો, Gross weight, Tare weight, scale/device reference, weighment slip reference અને નોંધ ભરવી.

શું AUTOMATIC થશે?

Net weight = Gross - Tare ગણાશે. Valid net weight સેવ થાય પછી સંબંધિત sale bill create/update થશે.

આગળ શું?

Accounts screenમાં bill number અને payable amount ઉપલબ્ધ થાય. Production versionમાં weighment operator અને scale timestamp જોડવાના.

ફાયદો: હરાજીનો ભાવ અને actual net weight એક જ transaction સાથે જોડાય; ખોટી quantity અથવા અલગ રેકોર્ડને કારણે થતો ગૂંચવાડો ઓછો કરી શકાય.
હાલ demoમાં વજન manually દાખલ થાય છે. Weighbridge/scale machineનું automatic data capture, calibration log, device serial verification અને network failure handling જોડવાનું બાકી છે.

Sales Bill / વેચાણ બિલ અને હિસાબ

Final quantity અને approved price પરથી settlement statement.

Screenshot 05 · Sale bill register
આ SCREEN શા માટે?

દરેક વેચાણનો bill number, linked Lot ID, farmer, buyer, net weight, rate અને amount એક જ જગ્યાએ રાખવા.

શું AUTOMATIC થશે?

Weighment પૂર્ણ થાય પછી demoમાં sale bill generate/update થાય છે. Gross value = net weight × auction rate.

USERએ શું ચકાસવાનું?

Gross amount, applicable approved seller-side deduction અને Farmer net payable તપાસવો. Buyer-side market fee/other duesને અલગ ledgerમાં રાખવા.

આગળ શું?

Farmer settlement screenમાં bill મુજબ ચુકવણી નોંધાય. Bill detailમાં transaction reference અને balances જોઈ શકાય.

ફાયદો: દરેક bill પાછળ auction ticket અને verified weighmentનો linkage હોવાથી હિસાબનો આધાર શોધવો સરળ બને.
કોઈપણ કપાત, માર્કેટ ફી, દર અથવા tax/charge productionમાં લાગુ કરતાં પહેલાં વર્તમાન કાયદા, Gujarat APMC Rules, applicable notifications અને સંબંધિત APMC bye-laws પ્રમાણે અધિકૃત મંજૂરી લેવી. Demo કોઈ કાનૂની દર નક્કી કરતું નથી.

06

Payments & Farmer Account / ચુકવણી અને ખેડૂત ખાતું

Bill-wise paid amount અને બાકી રકમ track કરવા માટે.

Screenshot 06 · Farmer settlement register
આ SCREEN શા માટે?

હરાજી પછી ખેડૂતને કેટલી રકમ ચૂકવવાની હતી, કેટલી ચૂકવાઈ, કેટલી બાકી છે અને Farmer Payment deadline ક્યારે છે તે સ્પષ્ટ રાખવા. આથી વેપારીની ખરીદ રકમ અને ખેડૂતનું payable એકબીજા સાથે ગૂંચવાય નહીં.

USERએ શું ભરવાનું?

Bill પસંદ કરવો, ચુકવણી રકમ, payment mode, UTR/transaction reference અને નોંધ દાખલ કરવી. Partial payment પણ record થઈ શકે.

શું AUTOMATIC થશે?

Paid amount વધશે, outstanding ઘટશે અને balance zero થાય ત્યારે bill/lot paid statusમાં જશે. Auction slipમાંથી farmer payment due date પણ auto-link થશે.

Buyer account અલગ કેમ?

ખેડૂતને ચૂકવવાની રકમ અને વેપારી પાસેથી વસૂલવાની ખરીદ રકમ બે અલગ હિસાબ છે. Trader Accountમાં purchase credit days, purchase limit અને outstanding દેખાય. Market fee / અન્ય statutory dues પણ અલગ ledgerમાં જ રહે.

ફાયદો: ખેડૂતની ચુકવણી બાકી છે કે પૂર્ણ થઈ છે તે bill-wise દેખાય; payment proof માટે UTR/reference note રાખી શકાય.
Demo payment માત્ર નોંધ છે - તે bank, UPI, NEFT કે RTGSમાં વાસ્તવિક પૈસા transfer કરતું નથી. Live payment integration અને bank reconciliation અલગથી બનાવવાના છે.

Trader Account & Credit Control / વેપારી ખાતું અને ખરીદ મર્યાદા

વેપારીનું રજીસ્ટ્રેશન, કેટલા દિવસમાં ખરીદ ચુકવણું કરવાનું અને કેટલો outstanding મંજૂર છે તે track કરવું.

Screenshot 07 · Trader master, credit days, purchase limit and outstanding ledger
આ SCREEN શા માટે?

વેપારીની ખરીદ રકમ કેટલી છે, કેટલી પ્રાપ્ત થઈ અને કેટલી બાકી છે તે અલગ trader-wise accountમાં રાખવા. ખેડૂતના payableથી વેપારીની વસૂલાત અલગ રહે.

અહીં શું configure થશે?

Trader name, APMC Registration / Licence ID, credit days અને maximum purchase outstanding limit. દરેક વેપારી માટે અલગ દિવસ અને રૂપિયા limit રાખી શકાય.

USERએ શું કરવાનું?

Accounts team પ્રાપ્ત થયેલી ખરીદ રકમ, payment mode અને UTR/reference bill-wise નોંધશે. Administrator વેપારીની credit policy update કરશે.

શું AUTOMATIC થશે?

Outstanding amount અને due date ગણાશે. અગાઉનું credit overdue હોય અથવા purchase limit વટે તો નવી auctionમાં તે buyerને પસંદ કરવા રોકી શકાય. Limitમાં unbilled auction exposure પણ ગણાય છે.

ફાયદો: કયા વેપારીએ કેટલી ખરીદ કરી, કેટલું ચૂકવ્યું, કેટલું બાકી છે અને કઈ partyની credit limit પૂર્ણ થઈ છે તે એક જ screenમાં જોવા મળે.
Credit days અને purchase limit APMC દ્વારા મંજૂર commercial / licence policy પ્રમાણે જ configure કરવા. આ demoમાં default days અને limits માત્ર ઉદાહરણ છે; કાયદાકીય universal limit નથી.

Gate Pass & Dispatch / ગેટ પાસ અને માલ રવાના

Settlement અને vehicle exit વચ્ચે અંતિમ control point.

Screenshot 08 · Dispatch register
આ SCREEN શા માટે?

માલના વેચાણ/ચુકવણી રેકોર્ડ પછી vehicleને yardમાંથી બહાર જવાની પરવાનગીનો record રાખવો.

USERએ શું કરવાનું?

Eligible Lot પસંદ કરવો, Gate Pass બનાવવો, vehicle અને transaction details ચકાસવી અને gate exit વખતે “Mark Dispatched” કરવું.

શું AUTOMATIC થશે?

આગળ શું?

Lotનું status “રવાના” થશે અને dispatch registerમાં દેખાશે. Productionમાં approved gate pass format, QR check અને supervisor override log જરૂરી.

ફાયદો: પૈસા/હિસાબની મંજૂરી અને vehicle exit વચ્ચે process control આવે; પછીથી કયા vehicleને ક્યારે pass અપાયો હતો તે શોધી શકાય.

Master Data & Settings / માસ્ટર ડેટા અને સેટિંગ્સ

યાર્ડ પ્રમાણે systemની મૂળભૂત configuration.

Screenshot 12 · Settings, master data and roles
આ SCREEN શા માટે?

યાર્ડનું નામ/code અને પાકની યાદી ઉપરાંત farmer payment deadline, માલ નિકાલ deadline, default trader credit days તથા દરેક વેપારીની registration અને purchase limit configure કરવા.

અહીં શું configure થશે?

Market committee name, yard code, timezone, ticket prefix, commodity master, role access, farmer payment deadline, stock-removal deadline, default buyer credit days, trader registration, buyer-wise purchase limit અને approved deductions.

USERએ શું કરવાનું?

અધિકૃત Administratorએ APMC resolutionથી મંજૂર payment/dispatch days, trader-wise credit days અને ખરીદ limit દાખલ કરવી. નવી commodity અથવા trader registration ઉમેરતા પહેલાં duplicate અને licence validity તપાસવી.

શું AUTOMATIC થશે?

નવી commodity entry/auction formમાં દેખાશે. Auction ticket બનાવતી વખતે Settingsના payment/dispatch days અને buyer masterના credit daysથી due dates auto-calculate થશે. Credit overdue / purchase limit full હોય તે buyer નવી auctionમાં block થશે.

અહીં દેખાતું Surat APMC Demo label માત્ર prototype ઓળખ માટે છે; તે Surat APMCની સત્તાવાર મંજૂરી અથવા અધિકૃત system હોવાનો દાવો નથી. Actual yard/committee વિગતો, permissions, rates અને bye-laws સંબંધિત અધિકારીઓ દ્વારા verify કરવા.

અમલમાં આવે તો કોને શું ફાયદો?

ખેડૂત

Farmer typeની ઓળખ, Farmer Registry ID તથા લાગુ રાજ્યનો land-record reference, serial ભાવ-કાપલી, ચુકવણી deadline અને paid/balance status.

ખરીદદાર / વેપારી

APMC registration ID, પોતાની ખરીદી, ખરીદ ચુકવણીની due date, credit days, purchase limit અને outstanding balance.

APMC સંચાલન

વાહન આવક, હરાજી pending/completed, yard stock by owner, dispatch/Gate Pass, farmer payable અને trader receivable એક dashboardમાં.

Gate staff

Vehicle, farmer અને lotની systematic entry; dispatchના અંતિમ control સાથે.

Accounts team

Bill-wise gross, net payable, payment reference, due balance અને buyer ledger.

Inspector / Auditor

Complaint linkage, activity history અને reports પરથી તપાસમાં મદદ.

આજના demoથી live APMC software સુધી શું બનાવવાનું બાકી છે?

  • Central database - એક userનો record બીજા userને તરત દેખાય.
  • Secure login, role permissions અને session management.
  • AgriStack / State Farmer Registry તથા state-wise land-record API verification અને consent.
  • Trader APMC registration / licence verification અને buyer-wise credit limit controls.
  • APMC-approved farmer payment, dispatch/removal deadline અને trader credit-day policy.
  • Server-side audit log અને approved correction/cancellation.
  • QR verification, unique serial policy અને duplicate print control.
  • Thermal/laser printer અને official slip formats.
  • Weighbridge/scale device integration તથા calibration controls.
  • Bank/UPI/NEFT integrations અને payment reconciliation.
  • SMS/WhatsApp receipts/notifications - approved provider સાથે.
  • Evidence upload, complaint assignment અને escalation.
  • Backup, restore, data retention, security testing અને monitoring.
  • Existing recordsનું migration અને reporting formats.
  • Official market rules, fees, bye-laws અને statutory process validation.

18 · RECOMMENDED IMPLEMENTATION PLAN

આગળનું કામ - સાથે મળીને યોગ્ય રીતે નક્કી કરવું

PHASE 1 · PROCESS DISCOVERY

અસલી યાર્ડની પ્રક્રિયા સમજવી

Gate entryથી dispatch સુધીના existing registers, slip formats, roles, approval steps, fees, dispute process અને daily reports એકત્ર કરવા. Gate, auction, weighment અને accounts staff સાથે walkthrough કરવો.

PHASE 2 · FINAL DESIGN

APMC પ્રમાણે screen અને rules finalize

દરેક field, seller identity model, state-wise Farmer ID / land-record reference, trader licence, payment/dispatch deadline, buyer-wise credit days અને purchase limit, correction control, ticket format, print copies, role matrix, QR access અને reports approve કરાવવા.

PHASE 3 · PRODUCTION BUILD

સાચું backend અને integrations

Central database, secure login, APIs, audit trail, backups, printer, scale device, bank/payment, notification અને evidence storage implement કરવું.

PHASE 4 · PILOT & GO-LIVE

એક મર્યાદિત flowથી pilot શરૂ

નક્કી કરેલા users/commodities પર test records ચલાવવા; manual register સાથે reconcile કરવું; training પછી approval લઈને staged go-live કરવું.

Final scope નક્કી કરવા APMC પાસેથી જરૂરી માહિતી
